# 예약·대기열 부하테스트 결과

**측정일** 2026-08-14 · **환경** 로컬 단일 인스턴스 (macOS, Docker MySQL 8.0 + Redis 7)
**대상** 사전예약 생성 경로 + 대기열(Waiting Room)

---

## 요약

정원 100석에 1,000명을 동시에 부었을 때, **정원 초과 없이 정확히 100건만 성공**했고 5xx는 한 건도 없었다. 대기열을 켜면 백엔드 유입이 설정값(50)에서 정확히 잘리고 개별 요청 지연이 자릿수 단위로 좋아진다.

테스트 과정에서 **정원의 절반만 팔리는 버그**를 발견해 수정했다.

---

## 1. 정원 정확성 (S1 — 대기열 없음)

정원 100 / VU 1,000 동시 요청.

| 항목 | 결과 |
|---|---|
| 예약 성공 | **100** |
| 매진 거절 (R004) | 900 |
| 5xx | **0** |
| 예약 지연 p50 | 824ms |
| 예약 지연 p99 | 1,097ms |
| 전체 소요 | 1.1초 |

DB 직접 검증:

| 검증 | 결과 |
|---|---|
| INV-1 정원 정합성 | `capacity=100, counter=100, actual_rows=100` ✅ 일치 |
| INV-2 1인 1매 | 위반 0건 ✅ |
| 예약 상태 분포 | CONFIRMED 100 |

> 애플리케이션 응답만 보지 않고 `fair_dates.reserved_count`와 `reservations` 실제 행 수를 함께 대조했다. 세 숫자가 전부 같아야 통과로 본다.

## 2. 대기열 유입 제한 (S4)

동일 부하 + 대기열 ON (`active_limit = 50`).

| 항목 | S1 (대기열 없음) | S4 (대기열) |
|---|---|---|
| 예약 성공 | 100 | 100 |
| 매진 거절 | 900 | 900 |
| 5xx | 0 | 0 |
| 예약 지연 p50 | 824ms | **24ms** |
| 예약 지연 p99 | 1,097ms | **327ms** |
| 예약 구간 동시성 | 1,000 | **50** |
| 전체 소요 | 1.1초 | 16.6초 |

### 읽는 법

**대기열은 빨라지는 장치가 아니다.** 전체 소요가 1.1초 → 16.6초로 늘어난 건 설계대로다. 1,000명을 50명씩 나눠 들여보냈으니 오래 걸리는 게 맞다.

의미는 다른 데 있다. **백엔드가 한 번에 감당하는 양이 1,000 → 50으로 눌렸고**, 개별 요청 지연이 p99 기준 1,097ms → 327ms로 떨어졌다. `active_limit`이 정확히 지켜진 것도 확인됐다(최대 동시 50).

**정원 정확성은 대기열과 무관하게 지켜졌다.** 대기열을 꺼도 성공은 정확히 100이었다. 정원을 지키는 것이 대기열이 아니라 DB 조건부 UPDATE라는 설계가 실측으로 확인된 셈이다.

## 3. 발견해서 고친 버그 — 슬롯 미반납

### 증상

프론트가 대기 슬롯을 **'대기 취소'를 눌렀을 때만** 반납하고 있었다. 무료 예약처럼 그 자리에서 끝나는 흐름도 슬롯을 TTL(12분) 내내 쥔 채 남았다.

### 영향

같은 부하(VU 300, 정원 100, `active_limit` 50)로 수정 전후를 비교했다.

| 항목 | 반납 안 함 (수정 전) | 반납 함 (수정 후) |
|---|---|---|
| 예약 성공 | **50** | **100** (정원 전량) |
| 대기 타임아웃 | **250** | 0 |
| 전체 소요 | 121.6초 | **5.2초** |

**정원이 100인데 50석만 팔리고 끝났다.** 먼저 통과한 50명이 자리를 놓지 않아 뒷사람이 영영 못 들어왔기 때문이다. 오픈 러시에서 이건 그대로 매출 손실이다.

### 수정

`releaseWaitingSlot(fairId)` 를 추가하고 시점별로 반납 여부를 나눴다.

| 시점 | 처리 | 이유 |
|---|---|---|
| 무료 예약 완료 | 반납 | 흐름이 끝났다 |
| 결제 완료 | 반납 | 결제까지 끝났다 |
| 매진·중복 등 최종 실패 | 반납 | 쓰지 않을 슬롯이다 |
| 유료 예약 → 결제 대기 | **유지** | 결제 API도 같은 슬롯으로 통과해야 한다 |
| 결제 승인 실패 | **유지** | 재시도할 수 있어야 한다 |

슬롯 수명(12분)이 결제 제한시간(10분)보다 길게 잡힌 이유가 네 번째 줄이다.

## 4. 이 결과의 한계

이 수치를 그대로 운영 용량 산정에 쓰면 안 된다.

- **단일 인스턴스다.** 멀티 인스턴스에서의 정책 캐시 전파(10초 TTL), 스케줄러 중복 실행은 검증되지 않았다.
- **같은 머신에서 부하를 만들었다.** 앱과 부하 생성기가 CPU를 나눠 쓰므로 **절대 수치(TPS)는 신뢰할 수 없다.** S1 대 S4의 상대 비교로만 읽어야 한다.
- **계측이 없다.** 커넥션 풀 대기, 락 대기, GC 같은 내부 지표가 없어서 "얼마나 느린지"만 알고 "왜 느린지"는 모른다.
- **결제 경로는 측정하지 않았다.** 외부 PG는 부하테스트 대상이 아니라 무료 행사로 측정했다.

## 5. 테스트 방법

### 설계상 넘어야 했던 제약

**1인 1매 제약** — `UK_RESERVATION_ACTIVE_USER_FAIR` 때문에 한 사용자는 한 행사에 활성 예약 1건뿐이다. 같은 계정으로 반복하면 2번째부터 전부 R005(중복예약)로 떨어져서 정원 경쟁이 아니라 중복 검사만 측정하게 된다. → **VU 수만큼 계정을 시드**했다.

**토큰 확보** — VU마다 다른 JWT가 필요하다. 토큰을 위조하는 대신 **실제 로그인으로 받았다.** JWT 시크릿을 몰라도 되고 "실제로 통과하는 토큰"임이 보장된다. 로그인은 부하 시작 전에 끝내므로 측정에 섞이지 않는다.

**결제 배제** — 예약금이 있으면 뒤에 토스 결제가 붙는다. **무료 행사**로 두면 예약이 한 트랜잭션에서 CONFIRMED까지 끝나 정원 경쟁만 깨끗이 남는다.

### 도구

k6 대신 Node로 작성했다(설치 불필요). 배포 환경에 부하를 걸 단계가 되면 k6로 옮긴다.

| 파일 | 역할 |
|---|---|
| `db/seed/loadtest-seed.sql` | 계정 2,000 + 무료 행사 + 운영일(정원 100) |
| `loadtest/run.mjs` | 부하 생성기 (`--scenario s1\|s4 --vus N`) |
| `loadtest/reset.sql` | 재실행 전 초기화 |
| `loadtest/verify.sql` | INV-1·INV-2 검증 |
| `loadtest/README.md` | 실행법 |

`--no-release` 플래그로 슬롯 미반납 상태를 재현할 수 있게 남겨뒀다. 이 회귀가 다시 생기면 바로 비교 가능하다.

## 6. 다음 단계

1. **계측 도입 (Phase 0)** — actuator + Micrometer로 커넥션 풀 대기, 락 대기, 예약 처리 시간을 지표화. 지금은 "왜 느린지"를 답할 수 없다.
2. **멀티 인스턴스 검증** — 배포 환경에서 정책 캐시 전파와 스케줄러 중복을 확인.
3. **Redis 장애 시나리오(S5)** — 부하 중 Redis를 죽여도 예약이 계속되고 성공 수가 여전히 정원과 일치하는지. 대기열 fail-open 설계의 핵심 검증이라 반드시 통과해야 한다.
